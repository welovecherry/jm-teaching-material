강의1 - OSI 7계층 모델

*총 120분*

**00-20분 네트워크를 배우는 이유 - 보안관제·기술영업 관점**

보안관제 담당자가 '왜 접속이 안 되나요'라는 고객 문의를 받았을 때, 네트워크 계층 구조를 모르면 원인을 좁혀갈 수 없다는 점을 사례로 제시한다. 2과목(네트워크·ZT)이 3~5과목(접근통제·이상탐지·SOAR)의 공통 배경지식이 됨을 강조한다.

*\[확인질문\] 고객이 '인터넷이 느려요'라고만 말했을 때, 어느 계층부터 확인해야 원인을 좁힐 수 있을까요?*

**20-50분 OSI 7계층 - 물리/데이터링크/네트워크 계층**

1계층(물리, 전기신호/케이블), 2계층(데이터링크, MAC주소/스위치), 3계층(네트워크, IP주소/라우터)의 역할과 대표 장비를 표로 정리한다. 각 계층에서 다루는 주소 체계(MAC vs IP)의 차이를 명확히 한다.

1계층: 케이블, 허브 - 전기신호

2계층: 스위치 - MAC 주소로 같은 네트워크 내 전달

3계층: 라우터 - IP 주소로 다른 네트워크 간 전달

*\[확인질문\] 같은 사무실 안의 두 PC가 통신할 때와, 인터넷 너머 서버와 통신할 때 주로 쓰이는 주소 체계가 다른 이유는 무엇일까요?*

**50-80분 OSI 7계층 - 전송/세션/표현/응용 계층**

4계층(전송, TCP/UDP·포트번호), 5~6계층(세션·표현), 7계층(응용, HTTP/DNS/SMTP 등)을 다룬다. 포트번호가 '같은 IP 안에서 어떤 서비스로 갈지'를 구분한다는 점을 강조한다.

포트 80: HTTP

포트 443: HTTPS

포트 22: SSH

포트 53: DNS

*\[확인질문\] 같은 서버(같은 IP)에서 웹사이트와 이메일 서비스를 동시에 운영할 수 있는 이유는 무엇일까요?*

**80-105분 계층 구조로 장애를 좁혀가는 법**

'물리 케이블은 꽂혀있는데 인터넷이 안 된다'와 같은 상황을 1계층부터 7계층까지 순서대로 점검하는 진단 흐름(bottom-up troubleshooting)으로 실습한다.

1\. 케이블/포트 연결 확인(1계층)

2\. 스위치 포트 상태 확인(2계층)

3\. IP 할당·핑 테스트(3계층)

4\. 포트 연결(telnet 등)(4계층)

5\. 서비스 응답 확인(7계층)

*\[확인질문\] 3계층(핑)까지는 성공했는데 4계층(포트 연결)이 실패한다면, 방화벽이 원인일 가능성이 있는 이유는 무엇일까요?*

**105-120분 정리**

OSI 7계층을 한 장 표로 정리하고 TCP/IP로 넘어간다.

강의2 - TCP/IP와 3-way Handshake

*총 120분*

**00-25분 TCP vs UDP**

TCP(연결지향, 신뢰성 보장)와 UDP(비연결, 빠르지만 신뢰성 없음)의 차이를 우체국 등기우편 vs 일반우편에 비유해 설명한다. 각각 어떤 서비스에 쓰이는지(웹=TCP, 스트리밍/DNS 질의=UDP) 예시를 든다.

*\[확인질문\] 화상회의(실시간 영상)와 파일 다운로드, 어느 쪽이 TCP에 더 적합할까요?*

**25-55분 3-way Handshake 상세**

SYN → SYN-ACK → ACK로 이어지는 TCP 연결 수립 과정을 순서도로 설명하고, 이후 이상탐지 과목에서 배울 SYN Flood 공격의 배경지식이 됨을 예고한다.

Client -\> Server: SYN (연결 요청)

Server -\> Client: SYN-ACK (승인+역요청)

Client -\> Server: ACK (승인)

= 연결 수립 완료, 데이터 전송 시작

*\[확인질문\] 만약 공격자가 SYN만 계속 보내고 ACK는 보내지 않는다면 서버에 어떤 부담이 생길까요?*

**55-85분 IP 헤더와 패킷 구조**

출발지/목적지 IP, TTL, 프로토콜 필드 등 IP 헤더의 핵심 필드를 소개하고, Wireshark 화면을 보며 실제 패킷에서 이 필드들을 찾아보는 실습을 진행한다.

*\[확인질문\] TTL(Time To Live) 값이 0이 되면 패킷은 어떻게 될까요?*

**85-110분 Wireshark 설치와 기본 사용법**

Wireshark 설치, 인터페이스 선택, 캡처 시작/정지, 필터(예: tcp.port==80) 사용법을 실습한다.

필터 예시:

ip.addr == 192.168.0.1

tcp.port == 443

http

*\[확인질문\] 특정 IP와 주고받은 패킷만 보고 싶을 때 어떤 필터를 쓸까요?*

**110-120분 실습 안내**

Wireshark로 직접 패킷을 캡처하고 3-way handshake를 눈으로 확인하는 실습을 안내한다.

실습 - 패킷 캡처·분석 실습

*총 120분*

**실습 목표:** Wireshark로 실제 패킷을 캡처해 3-way handshake와 IP/TCP 헤더 구조를 직접 확인한다.

**진행 단계**

1\. Wireshark를 설치하고 자신의 네트워크 인터페이스를 선택해 캡처를 시작한다

2\. 브라우저로 특정 웹사이트에 접속하며 동시에 패킷을 캡처한다

3\. 필터(tcp.port==443 또는 http)로 해당 트래픽만 걸러본다

4\. 캡처된 패킷 중 SYN, SYN-ACK, ACK 3개를 찾아 캡처 화면을 스크린샷으로 남긴다

5\. IP 헤더에서 출발지/목적지 IP, TTL 값을 확인해 기록한다

6\. network_zt/day01_packet_analysis.md에 캡처 결과와 관찰 내용을 정리한다

**산출물:** network_zt/day01_packet_analysis.md (캡처 스크린샷 포함)

**평가 기준**

\- 3-way handshake 3단계를 정확히 식별했는가

\- IP 헤더 핵심 필드(출발지/목적지/TTL)를 올바르게 읽었는가

\- 필터를 활용해 원하는 트래픽만 걸러냈는가

강의1 - IP 주소 체계와 서브네팅

*총 120분*

**00-25분 IPv4 주소 구조**

32비트 IPv4 주소를 8비트씩 4묶음(옥텟)으로 표현하는 방식, 공인IP·사설IP(10.x, 172.16~31.x, 192.168.x)의 차이를 설명한다.

192.168.0.1 = 11000000.10101000.00000000.00000001

*\[확인질문\] 회사 내부 PC들이 모두 192.168.x.x 대역을 쓰는데 인터넷은 어떻게 접속할 수 있을까요? (NAT 예고)*

**25-55분 서브넷 마스크와 CIDR 표기법**

서브넷 마스크가 네트워크 부분과 호스트 부분을 구분한다는 점, /24, /16 같은 CIDR 표기법을 읽는 법을 설명한다.

192.168.1.0/24

= 서브넷마스크 255.255.255.0

= 네트워크부 24비트 + 호스트부 8비트

= 호스트 254개 가능(2^8 - 2)

*\[확인질문\] /24보다 /28이 더 좁은 대역인데, /28에서는 몇 개의 호스트를 쓸 수 있을까요?*

**55-85분 서브네팅 계산 실습**

실제 기업 환경(영업팀 50대, 개발팀 30대, 서버팀 10대)을 가정해 필요한 서브넷을 설계하는 계산 실습을 진행한다.

영업팀: 192.168.10.0/26 (호스트 62개)

개발팀: 192.168.10.64/27 (호스트 30개)

서버팀: 192.168.10.96/28 (호스트 14개)

*\[확인질문\] 왜 팀마다 같은 대역을 나눠 쓰지 않고 서브넷으로 쪼갤까요? (보안·트래픽 분리 관점)*

**85-110분 NAT(Network Address Translation) 개념**

사설IP가 공인IP로 변환되어 인터넷과 통신하는 NAT의 기본 원리를 설명하고, 이것이 왜 '첫 번째 방어선'이 되는지 짚는다.

*\[확인질문\] NAT가 없다면 사내 PC 하나하나가 공인IP를 가져야 할 텐데, 어떤 문제(IP 고갈, 보안)가 생길까요?*

**110-120분 정리**

IP·서브네팅·NAT 핵심 개념을 정리하고 라우팅/VLAN으로 넘어간다.

강의2 - 라우팅 기본과 스위칭·VLAN

*총 120분*

**00-25분 라우팅이란 무엇인가**

라우터가 목적지 IP를 보고 다음 홉(hop)을 결정하는 과정을 라우팅 테이블 개념으로 설명한다. 기본 게이트웨이(default gateway)의 역할을 짚는다.

라우팅 테이블 예시:

목적지 192.168.20.0/24 -\> 다음 홉 10.0.0.1

기본 경로(0.0.0.0/0) -\> 인터넷 게이트웨이

*\[확인질문\] 라우팅 테이블에 없는 목적지로 가는 패킷은 기본적으로 어디로 보내질까요?*

**25-50분 정적 라우팅과 동적 라우팅**

관리자가 직접 경로를 입력하는 정적 라우팅과, 라우터끼리 자동으로 경로를 교환하는 동적 라우팅의 차이와 각각의 장단점을 비교한다.

*\[확인질문\] 소규모 지사 네트워크와 대형 통신사 백본망, 어느 쪽이 동적 라우팅이 더 필요할까요?*

**50-75분 스위치와 VLAN 개념**

물리적으로 같은 스위치에 연결되어 있어도 VLAN으로 논리적으로 다른 네트워크처럼 분리할 수 있다는 점을 설명한다. 보안 관점에서 VLAN 분리가 왜 중요한지 강조한다.

VLAN 10: 영업팀

VLAN 20: 개발팀

VLAN 99: 게스트 Wi-Fi (사내망과 완전 분리)

*\[확인질문\] 게스트 Wi-Fi를 VLAN으로 분리하지 않으면 어떤 보안 위험이 생길 수 있을까요?*

**75-100분 망 구성도에서 라우팅·VLAN 읽기**

실제 기업 망 구성도 예시(본사-지사, DMZ, 내부망)를 보여주며 어디가 라우터 구간이고 어디가 VLAN으로 분리된 구간인지 읽는 연습을 한다.

*\[확인질문\] 망 구성도에서 'DMZ'라고 표시된 구간은 왜 내부망과 분리되어 있을까요?*

**100-120분 실습 안내**

가상의 망 구성도를 보고 IP대역·라우팅 경로·VLAN 구성을 식별하는 실습을 안내한다.

실습 - 망 구성도 분석 및 서브네팅 설계

*총 120분*

**실습 목표:** 주어진 기업 시나리오에 맞는 서브넷을 설계하고, 망 구성도에서 라우팅 경로를 식별한다.

**진행 단계**

1\. 가상 A사 시나리오(본사 3개 부서, 지사 1곳, 서버실)를 확인한다

2\. 각 부서/지사에 필요한 호스트 수를 산정하고 알맞은 서브넷(/26, /27, /28 등)을 설계한다

3\. 설계한 서브넷 표를 network_zt/day02_subnet_design.md에 정리한다

4\. 제공된 망 구성도 이미지에서 라우터, 스위치, VLAN 경계를 표시해본다

5\. 본사에서 지사로 가는 패킷이 거치는 경로를 순서대로 적어본다

6\. 조원과 서로의 서브넷 설계를 비교하며 겹치는 대역이 없는지 교차 검증한다

**산출물:** network_zt/day02_subnet_design.md

**평가 기준**

\- 서브넷 계산(사용 가능 호스트 수)이 정확한가

\- 부서 간 대역이 겹치지 않는가

\- 망 구성도에서 라우팅 경로를 올바르게 식별했는가

강의1 - DNS 개념과 계층구조

*총 120분*

**00-20분 DNS가 필요한 이유**

사람은 도메인 이름(예: example.com)을 기억하지만 컴퓨터는 IP 주소로 통신한다는 점에서 DNS를 '인터넷의 전화번호부'에 비유해 설명한다.

*\[확인질문\] DNS가 없다면 웹사이트에 접속할 때마다 무엇을 외우고 있어야 할까요?*

**20-50분 DNS 계층구조 - Root, TLD, Authoritative**

루트 서버 → TLD 서버(.com, .kr 등) → 권위(Authoritative) 서버로 이어지는 계층 구조를 다이어그램으로 설명한다.

www.example.com 조회 순서:

1\. Root 서버: .com은 어디? -\> TLD 서버 주소 응답

2\. TLD(.com) 서버: example.com은 어디? -\> Authoritative 서버 주소 응답

3\. Authoritative 서버: www 레코드는? -\> 최종 IP 응답

*\[확인질문\] Root 서버가 다운되면 전세계 DNS 조회에 어떤 영향이 있을까요?*

**50-80분 재귀 질의 vs 반복 질의**

우리 PC가 사용하는 DNS 리졸버가 대신 여러 서버를 오가며 답을 찾아주는 재귀 질의와, 서버끼리 주고받는 반복 질의의 차이를 순서도로 설명한다.

*\[확인질문\] 우리 PC는 Root, TLD, Authoritative 서버에 각각 직접 물어보지 않는데 그 이유는 무엇일까요?*

**80-105분 주요 DNS 레코드 타입**

A(IPv4 주소), AAAA(IPv6), CNAME(별칭), MX(메일서버), TXT(검증용) 레코드의 용도를 표로 정리한다.

example.com. A 93.184.216.34

www.example.com. CNAME example.com.

example.com. MX 10 mail.example.com.

*\[확인질문\] www.example.com과 example.com이 같은 곳으로 연결되게 하려면 어떤 레코드를 쓸까요?*

**105-120분 정리**

DNS 계층구조와 레코드 타입을 정리하고 보안 이슈로 넘어간다.

강의2 - DNS 동작 실습과 보안 이슈

*총 120분*

**00-25분 nslookup/dig 명령어 실습**

nslookup(Windows)과 dig(Mac/Linux)로 도메인의 A 레코드, MX 레코드를 직접 조회하는 실습을 진행한다.

\$ nslookup example.com

\$ dig example.com MX

\$ dig +trace example.com

*\[확인질문\] dig +trace 명령은 무엇을 보여줄까요?*

**25-50분 DNS 캐싱과 TTL**

DNS 응답에도 TTL이 있어 일정 시간 캐싱된다는 점, DNS 레코드를 변경해도 즉시 전세계에 반영되지 않는다는 점(전파 지연)을 설명한다.

*\[확인질문\] 회사 웹사이트의 IP를 변경했는데 일부 사용자에게는 여전히 예전 사이트가 보인다면, 원인이 무엇일까요?*

**50-80분 DNS Spoofing/Cache Poisoning 개념**

공격자가 조작된 DNS 응답을 캐시에 주입해 사용자를 가짜 사이트로 유도하는 원리를 개념 수준에서 설명하고, 4과목 '비인가 접근·이상행위' 탐지 대상과 연결됨을 예고한다.

*\[확인질문\] 은행 사이트 도메인을 입력했는데 이상한 페이지가 뜬다면, DNS 관점에서 어떤 것을 의심해볼 수 있을까요?*

**80-105분 DNS 로그에서 이상징후 찾기**

정상적이지 않은 DNS 질의 패턴(무작위 문자열 도메인 대량 조회, DGA 개념)을 소개하고, 로그에서 어떤 특징을 봐야 하는지 짚는다.

정상: naver.com, google.com

의심: xjk3f9as0.com, q83nfoa2.net, ...(악성코드 C2 통신 특징)

*\[확인질문\] 무작위 문자열로 된 도메인을 짧은 시간에 대량으로 조회하는 PC가 있다면 무엇을 의심해볼 수 있을까요?*

**105-120분 실습 안내**

nslookup/dig로 여러 도메인을 조회하고 DNS 로그 샘플에서 이상징후를 찾는 실습을 안내한다.

실습 - DNS 조회 및 이상징후 식별

*총 120분*

**실습 목표:** nslookup/dig로 실제 도메인을 조회하고, DNS 로그 샘플에서 정상·비정상 패턴을 구분한다.

**진행 단계**

1\. nslookup(또는 dig)으로 5개 이상 도메인의 A, MX 레코드를 조회하고 결과를 기록한다

2\. dig +trace로 하나의 도메인에 대해 Root부터 Authoritative까지 전체 조회 경로를 확인한다

3\. 제공된 DNS 로그 샘플(정상 도메인과 DGA 스타일 도메인이 섞인 30줄)을 검토한다

4\. 무작위 문자열 패턴, 비정상적으로 짧은 TTL 등 의심 기준을 세워 이상 도메인을 골라낸다

5\. 골라낸 이상 도메인 목록과 판단 근거를 network_zt/day03_dns_analysis.md에 정리한다

6\. 조원과 서로 다른 판단 기준을 비교해보며 기준을 보완한다

**산출물:** network_zt/day03_dns_analysis.md

**평가 기준**

\- nslookup/dig 명령을 정확히 사용했는가

\- DGA 스타일 등 의심 도메인을 합리적 근거로 식별했는가

\- 판단 기준이 명확히 문서화되었는가

강의1 - VPN 개념과 종류

*총 120분*

**00-20분 VPN이 필요한 이유**

공용 인터넷을 통해 안전하지 않은 구간을 암호화된 터널로 연결해 마치 사설망처럼 통신하게 하는 VPN의 필요성을 재택근무·지사 연결 사례로 설명한다.

*\[확인질문\] 재택근무자가 회사 내부 시스템에 접속할 때 VPN 없이 접속하면 어떤 위험이 있을까요?*

**20-50분 Site-to-Site VPN**

본사-지사처럼 네트워크와 네트워크를 통째로 연결하는 Site-to-Site VPN의 구조를 다이어그램으로 설명한다.

본사 네트워크(192.168.10.0/24) \<-VPN 터널-\> 지사 네트워크(192.168.20.0/24)

*\[확인질문\] Site-to-Site VPN은 개별 직원이 아니라 무엇과 무엇을 연결하는 걸까요?*

**50-80분 Remote Access VPN**

개별 사용자가 자신의 PC/노트북에서 회사 네트워크로 접속하는 Remote Access VPN의 구조와, 클라이언트 프로그램·인증 절차를 설명한다.

*\[확인질문\] Site-to-Site VPN과 Remote Access VPN 중, 재택근무자 개인에게 필요한 것은 어느 쪽일까요?*

**80-105분 VPN과 Zero Trust의 관계(예고)**

전통적인 VPN은 '터널 안에 들어오면 신뢰'하는 경계 기반 보안 모델이라는 한계가 있다는 점을 짚고, 이것이 Zero Trust가 등장한 배경 중 하나임을 예고한다.

*\[확인질문\] VPN에 접속한 사람이 내부에서 아무 자원이나 접근할 수 있다면 어떤 위험이 있을까요?*

**105-120분 정리**

VPN 종류와 한계를 정리하고 방화벽으로 넘어간다.

강의2 - 방화벽 기본 개념과 정책 설계

*총 120분*

**00-25분 방화벽이란 무엇인가**

방화벽이 정해진 규칙(룰)에 따라 트래픽을 허용(Allow)하거나 차단(Deny)하는 장비/소프트웨어라는 점을 건물의 출입 통제에 비유해 설명한다.

*\[확인질문\] 방화벽 규칙이 하나도 없다면(모두 허용) 어떤 위험이 있을까요?*

**25-55분 방화벽 규칙 구성 요소**

출발지 IP, 목적지 IP, 포트, 프로토콜, 액션(Allow/Deny)으로 구성되는 방화벽 룰의 구조를 실제 룰 예시로 설명한다. 룰의 순서(위에서부터 순차 적용)가 중요하다는 점을 강조한다.

룰1: 출발지 any, 목적지 웹서버, 포트 443, Allow

룰2: 출발지 any, 목적지 웹서버, 포트 22, Deny

룰3(기본): 출발지 any, 목적지 any, Deny

*\[확인질문\] 룰1과 룰2의 순서를 바꾸면 결과가 달라질까요?*

**55-85분 화이트리스트 vs 블랙리스트 정책**

기본적으로 모두 막고 필요한 것만 허용하는 화이트리스트(최소권한) 방식과, 기본적으로 모두 허용하고 위험한 것만 막는 블랙리스트 방식을 비교한다.

*\[확인질문\] 새로운 공격 기법이 매일 등장하는 상황에서, 블랙리스트 방식만으로 충분히 방어할 수 있을까요?*

**85-110분 방화벽 정책 설계 실습 준비**

가상 시나리오(웹서버는 443만 외부 허용, DB서버는 내부망에서만 접근, 관리자는 특정 IP에서만 SSH 허용)를 제시하고 룰셋 설계 방법을 함께 시연한다.

*\[확인질문\] DB서버에 외부에서 직접 접근할 수 있게 열어두면 어떤 위험이 있을까요?*

**110-120분 실습 안내**

가상 시나리오에 맞는 방화벽 룰셋을 설계하는 실습을 안내한다.

실습 - 방화벽 정책 시나리오 설계

*총 120분*

**실습 목표:** 가상 기업 환경에 맞는 방화벽 룰셋을 화이트리스트 원칙으로 설계한다.

**진행 단계**

1\. 가상 A사 시나리오(웹서버, DB서버, 내부 사무망, 관리자 PC)를 확인한다

2\. 각 자원별로 누가/어디서/어떤 포트로 접근해야 하는지 요구사항을 정리한다

3\. 화이트리스트 원칙으로 룰셋을 설계한다

4\. 룰의 순서(구체적인 룰을 먼저, 기본 차단을 마지막에)를 고려해 배치한다

5\. network_zt/day04_firewall_ruleset.md에 룰셋 표를 작성한다

6\. 조원과 서로의 룰셋을 검토하며 불필요하게 넓게 열린 규칙이 없는지 점검한다

**산출물:** network_zt/day04_firewall_ruleset.md

**평가 기준**

\- 화이트리스트 원칙(최소권한)이 적용되었는가

\- 룰 순서가 논리적으로 배치되었는가

\- DB서버 등 민감 자원이 불필요하게 노출되지 않았는가

강의1 - 클라우드·SaaS 환경과 망 구성도

*총 120분*

**00-20분 IaaS/PaaS/SaaS 비교**

인프라(서버)만 빌리는 IaaS, 개발 플랫폼까지 제공되는 PaaS, 완성된 서비스를 그대로 쓰는 SaaS의 차이를 '집을 짓는 것 vs 완제품 아파트 임대'에 비유해 설명한다.

IaaS: AWS EC2, Azure VM

PaaS: AWS Elastic Beanstalk, Heroku

SaaS: 협업툴, 그룹웨어, CRM 서비스

*\[확인질문\] 회사가 자체 서버 없이 이메일·문서작업 서비스를 그대로 쓴다면 이는 어떤 유형일까요?*

**20-45분 SaaS 접속 흐름과 재택근무 확대의 영향**

사내 PC → 사내망 → 방화벽/프록시 → 인터넷 → SaaS 서버로 이어지는 접속 경로를 설명하고, 재택근무 확대로 VPN을 거치지 않고 SaaS에 직접 접속하는 경우가 늘면서 발생하는 가시성 이슈를 짚는다(Zero Trust 도입 배경 예고).

*\[확인질문\] 직원이 회사 VPN을 거치지 않고 집에서 바로 SaaS에 접속하면, 보안팀은 그 접속을 얼마나 파악할 수 있을까요?*

**45-70분 망 구성도의 표준 표기법과 DMZ**

라우터, 스위치, 방화벽, 서버를 나타내는 표준 아이콘과 선의 의미를 정리하고, 외부 공개 서버를 내부망과 분리된 DMZ 영역에 두는 이유를 설명한다.

인터넷 -- 외부방화벽 -- DMZ(웹서버) -- 내부방화벽 -- 내부망(DB, 사무망)

*\[확인질문\] 웹서버가 해킹당했을 때, DMZ 구조가 없다면 내부망까지 바로 위험해지는 이유는 무엇일까요?*

**70-95분 실제 망 구성도 읽기 실습**

본사-지사-클라우드가 혼합된 실제 스타일의 망 구성도 샘플을 보며 각 구간(내부망/DMZ/클라우드/VPN 터널)을 식별하는 실습을 진행한다.

*\[확인질문\] 이 구성도에서 SaaS로 나가는 트래픽은 어느 구간을 거치나요?*

**95-120분 draw.io로 망 구성도 작성 실습 준비**

무료 다이어그램 도구(draw.io)의 기본 사용법(도형 추가, 선 연결, 텍스트 입력)을 시연하고 실습을 예고한다.

강의2 - 네트워크 품질지표와 SaaS 지연 진단

*총 120분*

**00-20분 Latency·Jitter란**

패킷이 출발지에서 목적지까지 도달하는 데 걸리는 시간(Latency)과, 그 지연이 들쭉날쭉한 정도(Jitter)를 정의한다. 화상회의처럼 실시간성이 중요한 서비스에서 Jitter가 왜 특히 치명적인지 설명한다.

패킷1: 50ms, 패킷2: 52ms, 패킷3: 120ms, 패킷4: 48ms

= Jitter가 크다 (불안정)

*\[확인질문\] 평균 Latency는 낮은데 Jitter가 크면 화상회의 품질은 어떻게 느껴질까요?*

**20-45분 ping으로 Latency·Jitter 측정**

ping 명령으로 왕복시간(RTT)을 측정하고, 여러 번 측정한 값의 편차를 보며 Jitter를 가늠하는 실습을 진행한다.

\$ ping example.com

Reply from ...: time=45ms

Reply from ...: time=48ms

Reply from ...: time=112ms \<- 이상 징후

*\[확인질문\] ping 결과에서 유독 한 번만 응답시간이 크게 튄다면 무엇을 의심해볼 수 있을까요?*

**45-70분 Packet Loss와 traceroute**

패킷 손실(Packet Loss) 개념과 원인을 설명하고, traceroute/tracert로 출발지부터 목적지까지 각 구간의 지연을 확인하는 법을 실습한다.

\$ traceroute example.com

1 192.168.1.1 1ms

2 10.0.0.1 5ms

3 203.0.113.1 45ms \<- 여기서 지연 급증

4 example.com 46ms

*\[확인질문\] traceroute 결과에서 특정 홉에서만 지연이 갑자기 커진다면, 그 구간에 문제가 있다고 의심할 수 있는 이유는 무엇일까요?*

**70-95분 종합 진단 시나리오 - SaaS 접속 지연**

고객이 'SaaS 접속이 느리다'고 문의한 상황을 가정해, ping(Latency/Jitter) → traceroute(구간별 지연) → 방화벽/프록시 로그 순서로 원인을 좁혀가는 진단 흐름을 실습한다.

*\[확인질문\] ping은 정상인데 traceroute에서 특정 구간만 느리다면, 다음으로 무엇을 확인해야 할까요?*

**95-120분 실습 안내**

망 구성도 작성과 품질지표 측정·진단 리포트 작성 실습을 안내한다.

강의1 - Zero Trust 개념과 5대 원칙

*총 120분*

**00-20분 경계 기반 보안의 한계와 Zero Trust 등장**

'회사 네트워크 안은 안전하고, 밖은 위험하다'는 전통적 경계 기반 보안 모델을 설명하고, 재택근무·클라우드·SaaS 확산으로 '경계' 자체가 흐려진 현실(5일차 내용과 연결)을 짚는다. '아무도 기본적으로 신뢰하지 않고 매번 검증한다'는 Zero Trust의 핵심 철학을 설명한다.

*\[확인질문\] 직원이 이미 VPN으로 접속했다면, 내부의 모든 자원에 접근할 수 있게 하는 것이 왜 위험할까요?*

**20-55분 ZT 5대 원칙 개관 - ID·Device·Network**

ID(신원 검증, MFA), Device(기기 상태 검증, 백신·패치 여부), Network(마이크로 세그멘테이션)의 의미를 예시로 설명한다.

ID: 이 사용자가 진짜 김철수인가? (MFA)

Device: 이 기기는 회사 보안 기준을 충족하는가?

Network: 이 요청이 필요한 자원에만 도달하는가?

*\[확인질문\] 재택근무자가 개인 노트북(회사 보안 기준 미충족)으로 접속하려 한다면 ZT는 어떤 축에서 이를 걸러낼까요?*

**55-85분 ZT 5대 원칙 개관 - Application·Policy**

특정 앱에만 접근을 허용하는 Application 축과, 접속 시간·위치·위험도에 따라 정책이 동적으로 바뀌는 Policy 축(위험기반 인증)을 사례로 설명한다.

Application: 이 앱에 대한 접근 권한이 있는가?

Policy: 해외 IP에서 접속 시 추가 인증 요구

*\[확인질문\] 평소와 다른 국가에서 로그인 시도가 발생하면 Policy 축에서는 어떤 조치를 취할 수 있을까요?*

**85-110분 ZT vs 경계보안 비교표 작성**

경계 기반 보안과 ZT를 여러 기준(신뢰 전제, 검증 시점, 접근 범위)으로 비교하는 표를 함께 작성한다.

*\[확인질문\] 경계보안은 '한 번 들어오면 신뢰'하는 반면 ZT는 무엇을 매번 반복할까요?*

**110-120분 정리**

ZT의 5대 원칙을 정리하고 PDP/PEP 구조로 넘어간다.

강의2 - PDP/PEP 구조와 최소권한·지속검증

*총 120분*

**00-25분 PDP(Policy Decision Point)와 PEP(Policy Enforcement Point)**

'이 접근을 허용할지 판단하는 두뇌'인 PDP와, 그 결정을 실제로 집행하는 PEP의 역할을 설명한다. 판단과 집행이 분리되어 있는 이유를 짚는다.

사용자 접근 요청 -\> PDP(판단: 허용/거부/추가인증) -\> PEP(집행: 실제로 통과시키거나 차단)

*\[확인질문\] PDP가 '거부'라고 판단했는데 PEP가 이를 무시하고 통과시킨다면 어떤 문제가 생길까요?*

**25-55분 PDP/PEP 흐름 다이어그램**

구체적 시나리오(직원이 사내 앱에 접속 요청 → PDP가 ID/Device/상황 확인 → 결정 → PEP가 집행)를 순서도로 함께 그린다.

*\[확인질문\] 이 흐름에서 만약 기기 보안 상태가 기준 미달이면 PDP는 어떤 결정을 내려야 할까요?*

**55-80분 최소권한 원칙 복습과 심화**

업무 수행에 필요한 최소한의 권한만 부여한다는 원칙을 3과목(접근통제 자동화)과 연결지어 설명하고, ZT 관점에서는 이것이 '기본적으로 아무 권한도 없음(default deny)'에서 출발한다는 점을 강조한다.

*\[확인질문\] 신입사원에게 처음부터 모든 시스템 접근권한을 주는 것과, 필요할 때마다 요청받아 부여하는 것, ZT 철학에는 어느 쪽이 맞을까요?*

**80-105분 지속적 검증과 위험 기반 인증**

로그인 시점에 한 번만 검증하는 것이 아니라, 세션 내내 상태 변화를 지속적으로 재검증하는 개념과, 위험도에 따라 인증 강도를 동적으로 조절하는 위험 기반 인증을 설명한다.

로그인 시점: 정상 인증

30분 후: 다른 국가 IP로 갑자기 요청 발생 -\> 재검증 트리거 -\> 추가 인증 요구 또는 세션 종료

*\[확인질문\] 로그인 이후 세션을 끊지 않고 계속 유지한다면, 중간에 계정이 탈취되어도 이를 어떻게 알아챌 수 있을까요?*

**105-120분 보안 자세 점검·스코어링 개념 예고**

ID/Device/Network/Application/Policy 축과 최소권한·지속검증 개념을 종합해, 고객 환경의 ZT 성숙도를 점수화(스코어링)하는 접근법을 예고한다(캡스톤의 'ZT 보안 자세 점검·스코어링'과 직결).

예시 스코어링 항목: MFA 적용률(20점), 기기 보안 점검 비율(20점), 최소권한 준수율(20점), 마이크로세그멘테이션 적용 여부(20점), 위험기반인증 적용 여부(20점)

*\[확인질문\] 이런 점수 체계가 있으면, 고객사에게 '보안 수준이 어느 정도'라고 설명하기 더 쉬워질까요?*

강의1 - 정책 로그 구조와 필드 해석

*총 120분*

**00-25분 정책 로그란 무엇인가**

PDP/PEP가 접근 요청을 판단·집행할 때마다 남기는 로그(누가/언제/무엇에/어떤 결정)를 정책 로그로 정의하고, 이것이 왜 사후 감사·이상탐지의 핵심 데이터가 되는지 설명한다.

*\[확인질문\] 접근이 거부된 로그가 특정 사용자에게 반복적으로 쌓인다면 무엇을 의심해볼 수 있을까요?*

**25-55분 정책 로그 주요 필드**

timestamp, user, resource, action(allow/deny), reason, risk_score 등 정책 로그의 주요 필드를 실제 로그 예시로 보여주고 각 필드의 의미를 설명한다.

{

'timestamp': '2026-07-07T09:15:00',

'user': 'kim01',

'resource': 'hr-system',

'action': 'deny',

'reason': 'device_posture_fail',

'risk_score': 78

}

*\[확인질문\] 이 로그에서 접근이 거부된 이유는 무엇이며, 담당자는 무엇을 먼저 조치해야 할까요?*

**55-85분 정책 로그 패턴 분석**

단일 로그 한 줄이 아니라, 여러 로그를 모아봤을 때 드러나는 패턴(특정 시간대 거부 급증, 특정 리소스에 반복 시도 등)을 찾는 관점을 실습한다.

*\[확인질문\] 새벽 시간대에만 특정 리소스에 대한 deny 로그가 몰려있다면 무엇을 의심할 수 있을까요?*

**85-110분 정책 로그와 1과목 자동화 스킬의 연결**

1과목에서 배운 JSON 파싱·필터링 스킬이 정책 로그 분석에도 그대로 적용됨을 다시 확인하고, 로그 데이터를 구조화하는 관점을 복습한다.

*\[확인질문\] 1과목에서 만든 로그 필터링 함수를 이 정책 로그에도 그대로 쓸 수 있을까요?*

강의2 - 고객 환경 설명 문서화 기법

*총 120분*

**00-25분 기술 용어를 비전문가에게 설명하는 원칙**

고객(경영진, 비전공 담당자)에게 기술 내용을 설명할 때는 전문용어를 그대로 쓰지 않고 비유·결론 우선(두괄식)으로 전달해야 한다는 원칙을 사례로 비교한다.

전문가용: 'PDP가 device posture 기준 미달로 접근을 deny 처리했습니다'

고객용: '해당 직원의 노트북이 회사 보안 기준(백신 등)을 충족하지 못해 접속이 자동으로 차단되었습니다'

*\[확인질문\] 두 설명 중 고객이 바로 이해하고 다음 행동을 할 수 있는 쪽은 어느 것일까요?*

**25-55분 설명자료의 구조 - 결론, 근거, 권고**

고객 설명자료를 '결론(무슨 일이 있었나) → 근거(데이터·로그) → 권고(무엇을 해야 하나)' 3단 구조로 작성하는 템플릿을 제시한다.

*\[확인질문\] 근거(로그 데이터)를 결론보다 먼저 나열하면 바쁜 고객 담당자는 끝까지 읽을까요?*

**55-85분 시각 자료 활용**

표·간단한 그래프·다이어그램을 활용해 텍스트보다 빠르게 상황을 이해시키는 방법을 다룬다(5일차 망 구성도, 품질 리포트 경험과 연결).

*\[확인질문\] '접근 거부가 지난주보다 3배 늘었습니다'를 텍스트로만 쓰는 것과 간단한 막대그래프로 보여주는 것, 어느 쪽이 더 빠르게 전달될까요?*

**85-110분 설명자료 작성 실습 준비**

강의1에서 다룬 정책 로그 데이터를 바탕으로 비전문가용 설명자료를 작성하는 과제를 안내하고 예시 초안을 함께 검토한다.

**110-120분 실습 안내**

정책 로그를 분석해 비전문가용 고객 설명자료를 작성하는 실습을 안내한다.

실습 - 고객 설명자료 작성

*총 120분*

**실습 목표:** 정책 로그 샘플을 분석해 비전문가(고객 경영진)가 이해할 수 있는 설명자료를 작성한다.

**진행 단계**

1\. 제공된 정책 로그 샘플(30~50줄, allow/deny 혼재)을 검토해 패턴을 찾는다

2\. 가장 중요한 이슈 1~2가지를 선정한다

3\. 결론-근거-권고 3단 구조로 설명자료 초안을 작성한다(전문용어 최소화)

4\. 간단한 표 또는 막대그래프로 핵심 수치를 시각화한다

5\. network_zt/day07_customer_report.md로 저장한다

6\. 조원과 서로의 설명자료를 교환해 상호 검토한다

**산출물:** network_zt/day07_customer_report.md

**평가 기준**

\- 전문용어를 비전문가도 이해할 수 있게 풀어썼는가

\- 결론-근거-권고 구조를 따르는가

\- 핵심 이슈가 데이터에 근거해 명확히 제시되었는가

강의 - 이슈 유형 정리와 도식화 기법

*총 120분*

**00-20분 1~7일차 종합 지도**

OSI/TCP·IP → 서브네팅/라우팅 → DNS → VPN/방화벽 → 클라우드/품질지표 → ZT원칙/PDP·PEP → 정책로그/문서화까지의 흐름을 한 장으로 정리하며 오늘이 통합의 날임을 강조한다.

*\[확인질문\] 7일 중 가장 어렵게 느껴졌던 개념은 무엇이었나요?*

**20-45분 장애·위협·접근통제 이슈 유형 분류**

연결 장애·성능 저하·서비스 장애로 나뉘는 장애 유형, DNS 스푸핑·무차별 대입·SYN Flood 같은 위협 유형, 과다권한·최소권한 위반 같은 접근통제 이슈를 정책 로그 필드와 연결지어 정리한다.

*\[확인질문\] '특정 사이트만 안 열린다'는 증상은 어떤 장애 유형에 가까울까요?*

**45-70분 플로우차트·타임라인으로 이슈 도식화**

'증상 발생 → 진단 단계 → 원인 확정 → 조치'로 이어지는 흐름을 표준 플로우차트 기호로 표현하는 법, 사고 경위를 타임라인 형태로 표현하는 법(5과목 SOAR 초동대응 리포트와 연결)을 실습한다.

*\[확인질문\] 타임라인 형태로 사고를 정리하면, 표로 나열하는 것보다 어떤 점이 더 잘 보일까요?*

**70-95분 팀별 시나리오 도식화 작업**

팀(조)별로 장애/위협/접근통제 이슈 중 하나를 선택해, 배운 도식화 기법으로 대응 흐름을 표현하는 작업을 진행한다.

**95-120분 캡스톤 연계 안내 및 발표 준비**

network_zt/ 산출물(서브넷 설계, 방화벽 룰셋, 망 구성도, ZT 시나리오, PDP/PEP 흐름도, 정책 로그 분석)이 캡스톤의 'ZT 보안 자세 점검·스코어링' 기능에 재사용되는 전체 그림을 다시 확인시키고 발표를 준비시킨다.

실습 - 팀별 이슈 도식화 및 발표

*총 120분*

**실습 목표:** 장애·위협·접근통제 이슈 중 하나를 선택해 도식화하고, 학습을 종합해 팀별로 발표한다.

**진행 단계**

1\. 팀(조)별로 장애/위협/접근통제 이슈 시나리오 하나를 선택한다(예: DNS 스푸핑 의심 사고)

2\. 이슈 발생부터 대응까지의 흐름을 플로우차트 또는 타임라인으로 도식화한다

3\. 도식화 자료에 1~7일차에서 배운 개념이 어떻게 적용되는지 표시한다

4\. network_zt/day08_issue_diagram.png로 저장한다

5\. 5분 내외 발표 자료를 준비해 팀별로 발표한다

6\. 받은 피드백과 개선점을 network_zt/day08_retrospective.md에 정리해 캡스톤 착수 시 참고 자료로 남긴다

**산출물:** network_zt/day08_issue_diagram.png, network_zt/day08_retrospective.md

**평가 기준**

\- 이슈 대응 흐름이 논리적으로 도식화되었는가

\- 학습한 핵심 개념이 도식에 반영되었는가

\- 발표에서 캡스톤과의 연결점을 설명할 수 있는가
