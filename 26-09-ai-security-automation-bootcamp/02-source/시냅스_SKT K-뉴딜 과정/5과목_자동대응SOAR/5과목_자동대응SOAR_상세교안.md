강의1 - SOAR 개념과 플레이북 구조

*총 120분*

**00-20분 1~4과목 복습 - 탐지에서 대응으로**

1과목(자동화 기초) → 2과목(ZT PDP/PEP) → 3과목(접근통제 회수봇) → 4과목(이상탐지·위험점수)까지 '판단'을 자동화해왔다면, 5과목은 그 판단 이후 '실제 조치'까지 자동화하는 마지막 단계임을 강조한다.

*\[확인질문\] 4과목에서 만든 위험점수·우선순위 분류 결과를 가지고, 사람이 매번 수동으로 조치한다면 어떤 한계가 있을까요?*

**20-45분 SOAR란 무엇인가**

여러 보안 도구를 오케스트레이션(조율)하고, 반복적인 대응 작업을 자동화하며, 최종적으로 위협에 대응(Response)하는 SOAR의 3요소를 설명하고, 도입 시 과도한 자동화의 위험(오탐 시 자동 조치의 부작용)도 함께 짚는다.

Orchestration: 여러 도구를 연결

Automation: 반복 작업 자동 실행

Response: 실제 위협에 대한 조치

*\[확인질문\] 오탐(4과목)인 이벤트에 대해 자동으로 계정을 잠가버린다면 어떤 문제가 생길까요?*

**45-75분 플레이북(Playbook)이란 무엇인가**

특정 유형의 보안 이벤트가 발생했을 때 따라야 할 표준화된 대응 절차를 미리 문서화·코드화한 것을 플레이북으로 정의하고, 1과목 6일차에서 배운 트리거-조건-액션 모델을 확장해 트리거·조건·액션·승인의 4대 구성요소로 정리한다.

트리거: 이상탐지 모듈에서 risk_score \>= 80 이벤트 수신

조건: 사용자가 VIP 계정인가?

액션: 계정 임시 잠금 + 티켓 생성 + 담당자 알림

승인: VIP 계정은 잠금 전 보안팀장 승인 필요

*\[확인질문\] 1과목 6일차의 트리거-조건-액션 모델과 오늘의 플레이북, 무엇이 새로 추가되었나요?*

**75-100분 플레이북 예시와 문서화 템플릿**

4과목 상관분석 시나리오('로그인실패급증→성공→비인가접근')를 플레이북으로 구체화하고, 팀이 공유·검토할 수 있는 표준 문서 템플릿(이름, 트리거, 단계별 조치, 승인자, 예상 소요시간)을 실습한다.

*\[확인질문\] 플레이북에 '예상 소요시간'을 적어두면 실제 운영에서 어떤 점이 도움이 될까요?*

**100-120분 정리**

SOAR와 플레이북 구조를 정리하고 4단계 파이프라인 설계로 넘어간다.

강의2 - 탐지-분류-조치-보고 흐름 설계

*총 120분*

**00-20분 SOAR 4단계 파이프라인 개관**

탐지(Detect) → 분류(Triage) → 조치(Respond) → 보고(Report)로 이어지는 SOAR의 전체 파이프라인을 소개하고, 이후 각 단계를 실전으로 구현할 것임을 안내한다.

*\[확인질문\] 이 4단계 중 '분류(Triage)' 단계가 필요한 이유는 무엇일까요?*

**20-45분 이벤트 수집과 심각도 분류**

4과목 이상탐지 모듈에서 생성된 위험점수·우선순위가 매겨진 이벤트를 SOAR 파이프라인의 입력으로 받는 인터페이스를 설계하고, 우선순위·자산 중요도·영향 범위를 종합해 대응 등급(즉시 자동조치/승인 후 조치/모니터링만)을 정하는 분류 로직을 설계한다.

input_event = {'event_id': 'evt-2001', 'user': 'kim01', 'risk_score': 85, 'priority': 'high'}

등급 기준: high+낮은 영향범위 -\> 즉시 자동조치 / high+높은 영향범위(VIP) -\> 승인 후 조치

*\[확인질문\] 같은 high 우선순위라도 영향범위(일반 직원 vs 임원 계정)에 따라 왜 처리 방식이 달라야 할까요?*

**45-70분 조치 유형과 보고 단계 설계**

즉시 자동조치·승인 후 조치·모니터링만의 3가지 조치 유형을 정리하고, 조치가 끝난 후 무엇을 누구에게 보고할지를 1과목 9일차(보고서 자동생성)와 연결지어 설계한다.

*\[확인질문\] 1과목에서 만든 report_generator.py의 템플릿+LLM 결합 방식을 SOAR 보고서에도 그대로 쓸 수 있는 이유는 무엇일까요?*

**70-95분 이벤트 상태 관리와 플레이북 매칭**

각 이벤트가 4단계 중 어디까지 처리되었는지 상태(detected/triaged/responded/reported)로 추적하는 데이터 구조(3과목 요청 상태 관리 패턴 재사용)와, 분류된 등급·이벤트 유형에 따라 알맞은 플레이북을 자동 매칭하는 로직을 설계한다.

incident = {'event_id': 'evt-2001', 'status': 'triaged', 'history': \[...\]}

*\[확인질문\] 3과목에서 만든 요청 상태(requested-\>reviewing-\>approved) 관리 패턴과 오늘의 incident 상태 관리, 어떤 점이 비슷한가요?*

**95-120분 실습 안내**

SOAR 4단계 파이프라인 다이어그램과 이벤트 상태 관리 코드를 작성하는 실습을 안내한다.

강의1 - 계정 잠금 자동화

*총 120분*

**00-20분 계정 잠금이 필요한 상황과 부작용**

4과목에서 다룬 계정탈취 의심 시나리오에서 추가 피해를 막기 위한 첫 조치로 계정 잠금이 쓰이는 흐름을 설명하고, 정당한 사용자가 오탐으로 잠기면 업무가 중단되는 부작용도 함께 짚는다.

*\[확인질문\] 계정을 잠그지 않고 조사만 계속한다면, 공격자가 그 사이에 무엇을 할 수 있을까요?*

**20-50분 계정 잠금 시나리오 설계**

트리거(4과목 상관분석 매칭) → 조건(VIP 계정 여부로 자동/승인 분기) → 액션(임시 잠금 + 알림) → 해제 조건(조사 완료 후 수동 해제)으로 이어지는 시나리오를 설계한다.

*\[확인질문\] 임시 잠금에 자동 해제 조건이 없다면, 정당한 사용자는 얼마나 오래 업무가 중단될 수 있을까요?*

**50-80분 3과목 revoke.py와의 관계**

3과목에서 만든 권한 회수(revoke_permission)와 오늘의 계정 잠금이 비슷해 보이지만 다른 이유(회수는 특정 권한만 제거, 잠금은 전체 접근 차단)를 비교 설명한다.

*\[확인질문\] 3과목의 revoke_permission()과 오늘 만들 lock_account()의 차이는 무엇일까요?*

**80-105분 계정 잠금·해제 함수 구현**

lock_account(), unlock_account() 함수를 구현하고, 모든 조치는 사유·시각과 함께 로그로 남기도록 설계한다.

def lock_account(user, reason):

accounts\[user\]\['locked'\] = True

log_action('lock_account', {'user': user, 'reason': reason})

*\[확인질문\] 계정을 '영구 삭제'가 아니라 '임시 잠금'으로 설계하는 이유는 무엇일까요?*

강의2 - 접근 차단(IP차단·세션종료) 자동화

*총 120분*

**00-25분 IP 차단과 세션 종료의 차이**

IP 차단(2과목 방화벽 룰 재사용)은 네트워크 레벨 조치, 세션 종료는 애플리케이션 레벨 조치라는 점을 구분하고 각각 언제 쓰이는지 사례로 설명한다.

*\[확인질문\] 공격자의 IP가 계속 바뀐다면(VPN 등 사용), IP 차단만으로 충분할까요? 세션 종료가 왜 함께 필요할까요?*

**25-55분 IP 차단 자동화 구현**

2과목 4일차에서 배운 방화벽 룰 구조를 재사용해, 악성 IP를 방화벽 차단 목록 최상단에 자동 추가하는 함수를 구현한다.

def block_ip(ip, firewall_rules):

new_rule = {'src': ip, 'dst': 'any', 'action': 'deny', 'reason': 'SOAR auto-block'}

firewall_rules.insert(0, new_rule)

log_action('block_ip', {'ip': ip})

*\[확인질문\] 새 차단 규칙을 룰 리스트의 맨 앞에 추가하는 이유는 무엇일까요? (2과목에서 배운 룰 순서의 중요성)*

**55-85분 세션 종료 자동화 구현**

활성 세션 목록에서 특정 사용자의 세션을 찾아 무효화하는 terminate_session() 함수를 구현한다.

def terminate_session(user, active_sessions):

terminated = \[s for s in active_sessions if s\['user'\]==user\]

active_sessions\[:\] = \[s for s in active_sessions if s\['user'\]!=user\]

log_action('terminate_session', {'user': user, 'count': len(terminated)})

return terminated

*\[확인질문\] 세션을 종료해도 계정 잠금을 함께 하지 않으면 어떤 문제가 생길까요?*

**85-110분 VIP 계정 예외 처리와 차단 해제 절차**

VIP 계정 목록을 config로 분리해 lock_account() 호출 시 예외를 발생시켜 승인 절차로 우회하도록 하고, 차단 해제 시에도 반드시 사유를 로그로 남기는 절차를 설계한다.

*\[확인질문\] 차단은 자동으로 하고 해제는 왜 수동(사람 확인)으로 하는 것이 안전할까요?*

**110-120분 실습 안내**

계정잠금·접근차단 자동화 스크립트를 구현하는 실습을 안내한다.

실습 - 계정잠금·접근차단 자동화 스크립트 구현

*총 120분*

**실습 목표:** 계정 잠금, IP 차단, 세션 종료 자동화 함수를 구현하고 안전장치를 적용한다.

**진행 단계**

1\. soar_response/containment.py에 lock_account(), unlock_account(), block_ip(), terminate_session() 함수를 구현한다

2\. 모든 조치 함수 호출 시 log_action()으로 조치 이력을 남기도록 통일한다

3\. config/vip_accounts.json을 만들어 VIP 계정은 lock_account() 호출 시 예외를 발생시켜 승인 절차로 우회하도록 만든다

4\. 테스트 시나리오 3건(일반계정 자동잠금, VIP계정 승인필요, IP차단+세션종료 결합)을 실행해본다

5\. 차단 해제 함수(unlock_account, unblock_ip)도 구현하고 해제 시 반드시 사유를 기록하도록 만든다

강의1 - 티켓 생성 자동화

*총 120분*

**00-20분 왜 티켓 시스템과 연동하는가**

조치 이력을 로그 파일에만 남기면 팀 전체가 진행 상황을 공유하기 어렵다는 점을 짚고, 티켓 시스템(ITSM)과 연동해 추적 가능성(traceability)을 높이는 이유를 설명한다.

*\[확인질문\] 로그 파일만 있고 티켓이 없다면, '이 사고를 누가 지금 처리하고 있는지' 팀원들이 어떻게 알 수 있을까요?*

**20-50분 ITSM 연동 개념**

1과목 4일차에서 배운 API POST 요청 지식을 그대로 활용해, 가상의 티켓 시스템 API에 티켓을 생성하는 구조를 설명한다.

ticket_payload = {'title': '\[SOAR\] 계정탈취 의심 - kim01', 'priority': 'high', 'description': '...'}

*\[확인질문\] 1과목에서 만든 call_with_retry() 함수를 오늘의 티켓 생성 API 호출에도 재사용할 수 있는 이유는 무엇일까요?*

**50-80분 티켓 생성 자동화 구현**

1일차 플레이북 정보와 2일차 조치 이력을 결합해 티켓 본문을 자동 구성하고, 모의 API로 전송하는 create_ticket() 함수를 구현한다.

def create_ticket(incident, playbook, containment_actions):

body = f'플레이북: {playbook\["name"\]}\n조치내역: {containment_actions}'

payload = {'title': f'\[SOAR\] {incident\["event_id"\]}', 'priority': incident\['priority'\], 'description': body}

return requests.post(TICKET_API_URL, json=payload, timeout=5)

*\[확인질문\] 티켓 본문에 플레이북 이름과 조치내역을 자동으로 넣어주면, 담당자가 수동으로 무엇을 하지 않아도 될까요?*

**80-105분 티켓 상태와 incident 상태 동기화**

*\[확인질문\] incident 상태는 'responded'인데 티켓은 여전히 'Open'으로 남아있다면 어떤 혼란이 생길까요?*

강의2 - 알림 전파와 에스컬레이션

**25-55분 에스컬레이션 규칙 설계**

에스컬레이션 규칙:

0분: 1차 담당자(당직자)에게 알림

15분 무응답: 2차 담당자(팀장)에게 알림

30분 무응답: 3차(보안책임자) + 전화 알림

*\[확인질문\] 2과목에서 배운 SLA 초과 감지 로직(check_sla_breach)을 오늘의 에스컬레이션에도 재사용할 수 있는 이유는 무엇일까요?*

**55-85분 에스컬레이션 구현**

def escalate(incident, escalation_chain, response_status):

for level, contact in enumerate(escalation_chain):

if response_status.get(level) == 'acknowledged':

return

send_chat_alert(contact\['webhook'\], f'\[{level+1}차 에스컬레이션\] {incident\["event_id"\]}')

*\[확인질문\] 에스컬레이션 단계마다 알림 채널을 다르게 쓰는 이유는 무엇일까요?*

2과목 8일차에서 배운 타임라인 다이어그램 기법을 리포트 안의 '사고 경위' 섹션에 텍스트 형태로 적용하는 법을 실습한다.

**45-75분 데이터 취합과 템플릿 뼈대 구성**

incident(1일차), containment_log(2일차), ticket(3일차) 데이터를 하나로 취합하는 collect_incident_data() 함수를 구현하고, 1과목 9일차의 문자열 템플릿 방식을 재사용해 리포트 뼈대를 구성한다.

def collect_incident_data(event_id):

incident = load_incident(event_id)

actions = \[a for a in load_containment_log() if a\['event_id'\]==event_id\]

return {'incident': incident, 'actions': actions, 'ticket': ticket}

*\[확인질문\] 이 함수가 3개의 서로 다른 모듈의 데이터를 가져올 수 있는 것은 1~4과목에서 어떤 습관(JSON 저장, 공통 스키마)을 지켰기 때문일까요?*

강의2 - 승인 게이트와 오탐대응·운영 리스크 평가

*총 120분*

**00-20분 자동조치 vs 승인필요 조치 구분 기준**

1과목 6일차에서 예고했던 승인 게이트 개념을 SOAR 맥락에서 완성한다는 목표를 제시하고, 가역성·영향범위·확실성 3가지 기준으로 자동조치와 승인필요 조치를 나누는 프레임워크를 설명한다.

자동조치 가능: 낮은 위험 IP 차단(가역적, 영향범위 좁음)

승인 필요: VIP 계정 잠금, 핵심 서버 격리

*\[확인질문\] 가역적이지만 영향범위가 매우 넓은 조치가 있다면, 이것도 승인이 필요할까요?*

**20-50분 승인 게이트 공통 구현 패턴**

2일차 containment.py의 VIP 계정 예외 처리를 일반화해, 모든 조치 함수 앞에 공통 승인 게이트를 적용하는 execute_action() 함수를 구현한다.

def execute_action(action_func, \*args, risk_level='low', \*\*kwargs):

if risk_level in ('high', 'critical'):

return request_approval(action_func.\_\_name\_\_, args, kwargs)

return action_func(\*args, \*\*kwargs)

*\[확인질문\] 이렇게 공통 게이트를 만들면, 2일차에 만든 lock_account(), block_ip() 각각에 예외 처리를 따로 넣지 않아도 되는 이유는 무엇일까요?*

**50-75분 오탐 대응 절차와 피드백 루프**

자동으로 계정을 잠갔는데 알고 보니 정상 사용자였을 경우의 신속한 복구 절차(즉시 해제, 원인 기록)를 설계하고, 이 오탐 사례가 다시 4과목 evaluate_detector()에 라벨링 데이터로 추가되어 탐지 룰이 개선되는 피드백 루프를 설명한다.

*\[확인질문\] 이 피드백 루프가 있다면, 시간이 지날수록 이상탐지·SOAR 시스템의 오탐률은 어떻게 변화할까요?*

**75-100분 운영 리스크 종합 평가표 완성**

가역성·영향범위·확실성·오탐이력을 종합해 각 조치 유형별 운영 리스크 점수를 매기는 최종 평가표를 완성한다.

*\[확인질문\] 이 평가표가 있으면, 새로운 조치 유형을 추가할 때 승인 필요 여부를 어떻게 빠르게 결정할 수 있을까요?*

실습 - 초동대응 리포트·승인게이트·오탐대응 절차 구현
