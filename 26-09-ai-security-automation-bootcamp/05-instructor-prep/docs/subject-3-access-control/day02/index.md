# 3과목 Day 2 · 개요 — 접근 요청·승인·부여 프로세스 자동화

!!! note "이 Day 사용법"
    Day 1에서 "누가 무엇을 할 수 있나(RBAC)"를 만들었다면, Day 2는 그 권한을 **어떻게 신청하고, 누가 승인하고, 언제 부여·만료되는가**라는 **절차(process)**를 코드로 만듭니다. 오늘의 키워드는 **상태(status)**입니다.

> **오늘 한 문장:** 권한 부여를 사람이 눈대중으로 하지 않고, `요청 → 검토 → 승인/반려 → 부여 → 만료`라는 **정해진 상태 흐름**으로 자동화하고, 각 단계에 **SLA·이중승인·정책검증**을 붙입니다.
> **왜 배우나:** 실무 사고의 상당수는 "권한을 줬는데 왜 줬는지 기록이 없다"에서 옵니다. 오늘 만드는 요청-승인 로그가 **감사(audit) 추적**의 근거가 되고, 이 `create_request()`는 Day4의 '회수 승인'에도 **그대로 재사용**됩니다.

## 오늘의 최종 목표 (Day 2를 마치면)
- [ ] 권한 요청이 왜 '상태를 가진 흐름'이어야 하는지 설명한다
- [ ] 상태 전이(`requested→reviewing→approved→granted`)를 다이어그램으로 그린다
- [ ] SLA(처리기한)와 이중승인이 왜 필요한지 안다
- [ ] `approve_request()`가 "잘못된 상태에서의 승인"을 어떻게 막는지 한 줄씩 설명한다
- [ ] `check_sla_breach()`로 기한 초과 요청을 걸러낸다
- [ ] Day1의 `evaluate_access()`를 승인 로직에 연동한다
