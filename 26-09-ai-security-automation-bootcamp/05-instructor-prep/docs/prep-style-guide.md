# 예습 문서 스타일 가이드

이 사이트(강사 예습 튜토리얼)의 **모든 Day 문서는 이 규칙대로** 씁니다.
학생용 노트북 규칙(`_shared/notebook-style-guide.md`)과는 **목적이 반대**이므로 헷갈리지 않습니다.

| | 학생용 노트북 | 이 예습 문서 |
|---|---|---|
| 읽는 사람 | 수강생 | **강사 본인** |
| 목적 | 빈칸 채우며 **배운다** | 내가 먼저 **완전히 이해해 가르칠 수 있게** 된다 |
| 빈칸/퀴즈 | 남겨둔다 | **남기지 않는다**(정답까지 다 적음) |
| 핵심 질문 | "이거 풀어보세요" | "학생이 뭘 물어볼까 / 나는 어떻게 설명할까" |

---

## 1. 핵심 원칙 5가지

1. **아주 쉽게.** 중학생에게 설명하듯. 어려운 말은 반드시 쉬운 말로 한 번 더 풀어씁니다.
2. **왜 배우는지 먼저.** 개념을 던지기 전에 "이걸 왜, 어디에 쓰는가"를 한 줄이라도 먼저 답합니다.
3. **단계적으로.** 큰 개념 → 작은 조각 → 예시 → 실무 순서로, 계단 오르듯 잘게 나눕니다.
4. **읽기 편하게.** 긴 문단 금지. 짧은 문장, 표, 목록, 콜아웃 상자를 적극 씁니다.
5. **실무 감각.** "현장에서는 이렇게 쓴다 / 이때 실수한다"는 팁을 곁들입니다.

## 2. 영어 용어는 한글 발음 병기 (필수)
영어·약어가 처음 나오면 **( ) 안에 한글 발음**을 넣고, 바로 뒤에 쉬운 뜻을 붙입니다.
> ⚠️ **첫 등장 위치에서** 병기한다 — **제목·요약·시간표 등 문서 앞부분**에서 처음 나오면 거기서
> 바로 붙인다. 본문 중간에서만 붙이면 위에서부터 읽는 사람은 발음을 못 본다(예: RBAC은
> 제목·요약의 첫 등장에서 `RBAC(알백)`으로).

> **OSI(오에스아이) 7계층** — 네트워크 통신을 7개 층으로 나눠 설명하는 지도.
> **handshake(핸드셰이크, "악수")** — 통신을 시작하기 전에 서로 "준비됐니? 응 됐어" 하고 맞춰보는 인사 절차.
> **payload(페이로드, "실어 나르는 짐")** — 포장(헤더)을 뺀, 실제로 전달하려는 알맹이 데이터.

- 약어는 **풀어쓴 영어 + 한글발음 + 뜻** 3종 세트: `RBAC(알백, Role-Based Access Control, 역할 기반 접근통제)`
- 같은 용어가 다시 나오면 발음 병기는 생략해도 됩니다(처음 한 번만).

## 3. 문서 말투

- **~습니다 / ~합니다** 체. 차분하고 친절하게.
- 코드·값·명령어·필드명은 영어 그대로, 백틱으로 감쌉니다: `tcp.port == 443`, `TTL`.
- 코드 안 주석은 한국어로 답니다.

## 4. 콜아웃(강조 상자) 사용법
MkDocs Material의 admonition을 씁니다. 종류를 **의미별로 고정**합니다.

```
!!! question "확인질문"     ← 상세교안의 [확인질문]에 내가 미리 답
!!! tip "실무 팁"                     ← 현장에서 이렇게 쓴다
!!! warning "학생이 헷갈리는 지점"     ← 자주 나오는 오해·질문
!!! example "쉬운 비유"               ← 일상 비유로 이해시키기
!!! note "한 줄 요약"                 ← 블록 끝 정리
```

접어두기(길면)는 `???`를 씁니다: `??? note "더 깊이 (심화)"`.

## 5. Day 폴더 구조 (확정) — 교시별 페이지 분할
한 Day는 6시간(강의1+강의2+실습)이라 한 파일에 다 넣으면 스크롤 지옥이 된다.
**폴더 = Day, 파일 = 교시**로 나눠 사이드바를 계층화한다.
```
subject-N-topic/
  dayDD/
    index.md      # Day 개요: 시간표(하루 전체) + 어려운 개념 풀기 + 최종 목표
    lecture1.md   # 강의1 (오전) — 상단(시간표 아래)에 '이 교시에 나오는 어려운 용어' 표 포함
    lecture2.md   # 강의2 (오후) — 상단에 용어 표 포함
    practice.md   # 실습 (120분) — 강사가 직접 해보고 함정 기록
```
nav도 `Day 1 → ①개요 / ②강의1 / ③강의2 / ④실습`으로 중첩한다.

**🔬 깊이 보기 (필수 패턴):** 중요 개념(MAC 주소, 3-way Handshake, 서브네팅 등)은
본문 안에 `### 🔬 깊이 보기 — OO 완전정복` 블록을 만들어 **1단계·2단계… 단계적 튜토리얼**로
따로 판다. 분량과 깊이를 동시에 채우는 핵심 장치.

## 6. Day(교시) 문서의 뼈대 (고정 틀)
```markdown
# N과목 Day D · 제목

> **오늘 한 문장:** (이 하루/교시를 한 문장으로)
> **왜 배우나:** (이걸 배우면 뭘 할 수 있나)

## 오늘의 시간표            ← (필수) 상세교안 블록/시간 표 그대로
| 시간 | 주제 | 핵심 한 줄 |

## 이 시간에 나오는 어려운 개념 쉽게 풀기   ← (필수) 시간표 바로 아래
표 하나로, 이 시간에 등장하는 어려운 용어를 미리 아주 쉽게 풀어둔다.
| 용어(한글발음) | 한 줄 뜻(중학생도 알게) | 비유 |
> 본문에서 그 용어가 처음 나올 때 한 번 더 풀어써도 됨(중복 OK).

---

## 강의1 · (제목)  *총 120분*

### ⏱️ 00-20분 · (소제목)
**🎤 이렇게 문을 엽니다** — 실제 도입 멘트 예시
**🧠 쉽게 이해하기** — 내 말로 + 비유 + 왜 중요한지 (용어 한글발음 병기)
   · 개념을 여러 조각으로 잘게 나눠, 조각마다 예시를 붙인다
   · 실제 명령어·화면·시나리오 워크스루로 "눈에 보이게" 만든다
!!! example "쉬운 비유"
!!! warning "학생이 헷갈리는 지점"
!!! tip "실무 팁"
!!! question "확인질문"

### ⏱️ 20-50분 · ...
(블록 반복 — 배정 시간에 맞는 분량으로, 아래 6번 규칙 준수)

## 강의2 · ...
## 실습 · ...   ← 실습은 내가 먼저 직접 해본 결과·함정을 적음

---

## ✅ 가르칠 준비 체크리스트
- [ ] 이 개념을 비유 없이도, 비유를 들어서도 설명할 수 있다
- [ ] 확인질문 O개에 막힘없이 답할 수 있다
- [ ] 학생이 자주 하는 질문 O개에 답을 준비했다
- [ ] 실습을 내 손으로 처음부터 끝까지 해봤다
```

## 7. 분량 규칙 — "시간을 채운다" (중요)
예습 문서는 **강의 실제 진행 분량**이어야 한다. 강사가 눈으로 5분에 읽을 양으로는
30분을 강의할 수 없다. 각 시간 블록은 **배정 시간(예: 20-50분 = 30분)을 실제로 채울**
깊이로 쓴다. 얇으면 다음을 늘려 채운다:

- 개념을 더 잘게 쪼개고, **조각마다 구체 예시**를 붙인다
- **실제 명령어·화면·주소 예시**(예: `arp -a`, MAC `00:1A:2B:...`)를 넣는다
- **데이터가 흐르는 시나리오 워크스루**(단계별)를 넣는다
- **학생이 자주 하는 질문**과 그 답을 미리 적는다
- 관련 **실무 사례/실수담**을 곁들인다
> 기준 감각: 상세교안 원문 몇 줄을, 30분 강의가 되도록 "펼쳐" 쓴다.

## 8. 파일 네이밍

- 샘플 버전은 **숫자 버전**(`v1`, `v2`, `v4` …)을 쓴다(설명형 접미사보다 숫자 선호).
- 문서 제목(H1)에 사람이 읽을 이름을 명확히 적는다.

## 9. 강의 중 인터랙티브 퀴즈 (확정 형식)
강의1·강의2 등 개념 페이지 **곳곳(섹션마다)**에 인터랙티브 객관식을 촘촘히 넣는다.
정답을 누르면 즉시 채점되는 위젯(`assets/quiz.js`)을 쓴다.

**형식 규칙 (반드시)**

1. **4지선다 객관식.** 단, ==보기(문항)는 명사 단답이 아니라 "짧은 서술형 문장"==으로 쓴다.
   - ❌ 나쁜 예(암기형): "포트 443은? ① HTTP ② HTTPS ③ SSH ④ DNS"
   - ✅ 좋은 예(맥락형): "핑은 되는데 443만 안 열릴 때 방화벽을 의심하는 근거는? ① 핑이 됐다는 건 IP(3계층)까지 도달했다는 뜻이라 막힌 곳은 포트를 통제하는 4계층일 가능성이 높기 때문 …"
2. **목적은 "왜 이게 답일 수밖에 없는지" 맥락 이해** — 암기 확인이 아니다.
3. **질문은 "왜 / 이유 / 가장 적절한 설명"** 프레이밍으로.
4. **오답 보기도 "그럴듯한 잘못된 이유(오개념)"**로 만든다 → 고르는 과정 자체가 개념 교정.
5. **난이도는 쉬움과 어려움 사이(중간).** 계산 함정보다 "상황 이해"로 난이도를 준다.
6. 해설에는 **정답 이유 + "다른 보기가 왜 틀렸는지"**를 함께 적는다.
7. 가끔 **O/X**(보기 2개)도 섞는다. 서술형이 필요하면 "객관식인데 보기가 문장"으로 낸다
   (자유 서술형은 자동 채점이 안 되므로 지양, 필요 시 모범답안 토글).

**위젯 HTML 패턴** (블록 내부에 빈 줄 없이):
```html
<div class="quiz">
<p class="quiz-q"><span class="tag">퀴즈</span><b>질문(왜/이유)?</b></p>
<button class="quiz-opt">그럴듯한 오답 문장</button>
<button class="quiz-opt" data-correct>정답 문장(왜를 담은)</button>
<button class="quiz-opt">그럴듯한 오답 문장</button>
<button class="quiz-opt">그럴듯한 오답 문장</button>
<div class="quiz-explain"><b>정답: …</b> 왜 맞는지 + 다른 보기가 왜 틀렸는지.</div>
<button class="quiz-retry">다시 풀기</button>
</div>
```

## 10. 하지 말 것

- 긴 벽 같은 문단 (3~4줄 넘어가면 쪼갠다)
- 발음·뜻 없이 영어 약어만 던지기
- 상세교안에 없는 내용을 지어내기 (원본이 기준)
- 학생용처럼 빈칸/미완성으로 남기기 (예습은 정답본)
- **배정 시간에 못 미치는 얇은 분량**(7번 위반)
- **암기형·단답 명사 보기 퀴즈**(9번 위반 — 보기는 맥락 담은 문장으로)
- **리스트(`- `, `1. `) 앞에 빈 줄 생략** — 앞 문장과 리스트 사이에 **반드시 빈 줄**을 둔다.
  없으면 Python-Markdown이 리스트로 인식 못 하고 한 문단으로 뭉쳐 렌더된다(가독성 파괴).
  콜아웃 상자 안에서도 동일(`!!! ...` 제목 다음 첫 리스트 앞에도 빈 줄).
